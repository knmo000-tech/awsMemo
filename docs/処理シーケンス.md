# 処理シーケンス

```mermaid
sequenceDiagram
    autonumber
    participant C as WPF
    participant G as API Gateway REST API
    participant A as API Lambda (FastAPI)
    participant D as DynamoDB
    participant W as Worker Lambda
    participant B as Bedrock
    participant S as S3
    C->>G: POST /auth（保守キー・顧客名）
    G->>A: 認証要求
    A->>D: Customers照合
    D-->>A: 顧客情報
    A-->>C: JWT
    C->>G: POST /jobs（JWT・入力）
    G->>A: ジョブ受付
    A->>D: JobsへQUEUED登録
    A-)W: 非同期Invoke
    A-->>C: 202 jobId
    W->>D: RUNNING更新
    W->>B: モデル呼び出し
    B-->>W: 生成JSON・トークン使用量
    W->>D: 使用量記録（保存先の詳細設計は未確定）
    W->>S: JSON保存（application/json）
    W->>D: SUCCEEDED更新
    loop 完了までポーリング
        C->>G: GET /jobs/{jobId}（JWT）
        G->>A: 状態照会
        A->>D: Jobs取得・顧客所有者照合
        D-->>A: 状態・成果物キー
        A-->>C: 状態 / 完了時は署名付きURL
    end
    C->>S: 署名付きURLでJSON取得
    S-->>C: JSON
```

**`POST /auth`は初回・JWT期限切れなどの再認証時のみ実行。** WPFは有効なJWTを保持し、ジョブ投入・ポーリングで再利用する。API Lambdaは各リクエストでJWTを検証する。

異常時は`FAILED`とエラーコードを記録。非同期再試行・重複起動・S3保存後の状態更新失敗に備え、冪等性と復旧処理を設計する。

## 2026-10-19：SQS導入時の差分（未確定）

上のシーケンス図は従来の直接非同期Invoke方式。SQS採用時は `API Lambda → SQS → Worker Lambda` に置き換える。

- APIがDynamoDBへ`QUEUED`登録し、SQSへメッセージを送信。片側のみ成功した際の回復処理を設ける。
- `MessageGroupId`はJWTなどからサーバー側で確認した`customerId`を使用し、WPFからの値を信用しない。
- Workerは重複配送でも安全に動作させ、条件付き状態遷移と一意な使用量イベントで二重請求を防ぐ。ただし二重推論そのものは失敗状況により完全排除できない可能性がある。
- 詳細：[ADR-0009](adr/0009_SQS公平キュー導入検討.md)。
