# ADR-0003: 顧客・ジョブ・トークン使用量の永続化

- **日付**: 2026-10-13（Customers/JobsとCSV保存方針は以前から検討）
- **ステータス**: 原則を採用 / 使用量明細の物理設計は検討中

## 背景

複数の顧客企業がインターネットからAPIを利用する。**顧客ごとのBedrockトークン使用量に独自の料金計算を適用して請求する**。請求の根拠となる使用量の完全性、正確性、重複排除、説明可能性が最重要。

## 現時点の方針

- **DynamoDB（採用）**: Customersで顧客の認証情報、Jobsで処理状態と所有顧客を管理する。
- **S3（採用）**: 非公開で生成CSVを保管し、認可後に期限付き署名URLで取得させる。
- **トークン実績をDBに保存する要件（採用）**: WPFから申告された数値は課金根拠にせず、Bedrockレスポンス等のサーバー側の確定値を記録する。
- **UsageEventsテーブル案（検討中）**: ジョブ単位の使用量実績を追記型イベントとして記録する。物理テーブルの分割・キー設計・集計方式は未決定。

## 提案するUsageEventsの情報例

| フィールド | 用途 |
| --- | --- |
| `usageEventId` / `invocationId` / `jobId` | 追跡・重複排除 |
| `customerId` | 請求先の識別。認証からサーバー側で確定 |
| `modelId` / `modelVersion` | 利用モデル・請求単価区分 |
| `inputTokens` / `outputTokens` | 実際の入出力トークン数 |
| `cacheReadTokens` / `cacheWriteTokens`（該当時） | キャッシュを使う場合の単価区分 |
| `pricingVersion` / `usageTimestamp` | 過去の請求再計算と監査 |
| `requestId` / `status` | AWS側の呼び出し結果との突合 |

## 採用理由と不採用案

- **DynamoDB採用**: ジョブID/顧客IDによる照会、API・Workerからの状態管理を単純化。クエリ要件が高度になればRDBや集計専用ストアを再評価。
- **S3採用**: 生成CSVをDBに格納せずオブジェクトとして保管でき、短命URLで安全に配布可能。
- **WPF側でトークン申告する案を不採用**: 利用者が改変可能で請求の信頼性を担保できない。
- **Jobsの累積トークン数だけを上書きして請求する案を推奨しない**: 明細や価格改定履歴を追いにくく、修正時の追跡も難しい。

## 請求データ保護方針（詳細は別ADR）

1. IAM: API Lambdaには請求実績の任意更新権限を与えず、使用量記録処理だけに必要操作を許可。
2. DynamoDBの `PutItem` を使う場合は条件式 `attribute_not_exists` 等で既存イベント上書きを防止。
3. 再試行・二重実行時も重複請求がないよう一意性・冪等性を実装。生成済なのにレスポンス未受信だったケースを含め、Bedrockの実際の請求利用量との突合方針を決める。
4. DynamoDB PITR、CloudTrailデータイベント、アプリ監査ログで復旧・証跡を整備する。
5. 請求明細の確定版を別保管し、S3 Object Lock等による保持/改ざん耐性を**検討**する。
6. 単価バージョンを含む請求スナップショットと、修正は上書きではなく訂正イベント方式を検討する。

## 請求ポリシーに関する未決定事項（2026-10-14）

Bedrockでトークンが消費された後、CSV生成・保存・結果返却が失敗したときの**顧客への請求可否は要検討**。実消費の記録と顧客に請求するかという業務判断を分け、失敗の種類ごとの請求／非請求／調整ルールをレビューで決める。現段階では採用済みの課金ルールとして扱わない。

検討経緯は [請求データ設計メモ](../billing-data-design-notes.md) と [デザインレビュー草稿](../reviews/aws-design-review-v0.2.md) を参照。

## 出力形式に関する後続決定

2026-10-15：成果物の形式をCSVからJSONへ変更。S3保存と署名付きURL取得は維持。請求データの設計方針や未決定の請求ポリシーは変わらない（[ADR-0007](0007-output-json.md)）。

## 未決事項

テーブルのPK/GSI、原子的なイベント記録方法、Bedrock利用量の取得先と例外時補正、顧客単位のクォータ、請求締めタイミング、データ保持期間、税率/価格改定を含む計算仕様。

## 再検討条件

利用企業数や集計の複雑化、請求紛争、コンプライアンス/証跡要件の強化、利用量と請求額の不一致が発生したとき。

## DB詳細設計時の検討メモ

別テーブル化とIAM権限分離、DynamoDBの条件付き追記、監査・復旧、請求の整合性をまとめた [請求データ保護・DB詳細設計の検討メモ](../billing-data-design-notes.md) を参照。**物理テーブル構造や追加Lambdaの採否はまだ確定していない**。
