# ADR-0001: API LambdaにFastAPI + Mangumを採用

> **現在の適用範囲（2026-10-25）：** FastAPI＋MangumはREST案の実装候補。入口方式の再評価に伴い現在は条件付き適用。Web案ではNode.jsのHTTPアプリを検討する。 [検討状況](../current/検討状況.md) / [後続ADR-0010](0010_不透明トークン前提と入口方式の再評価.md)。以下は当時の判断記録。

- **決定日**: 2026-10-13（初回比較: 2026-10-07）
- **当時のステータス**: 採用（設計確定）、実装未確認

## 背景

WPFクライアントから `POST /auth`、`POST /jobs`、`GET /jobs/{jobId}` のAPIを呼ぶ。LambdaのPythonランタイムにはFastAPIが同梱されないため、依存パッケージの管理が必要。

## 決定

API Lambdaでは **FastAPI + Mangum** を使う。FastAPIがルーティング・スキーマ検証・OpenAPI生成を担い、MangumでAPI GatewayのLambdaイベントをASGIに変換する。Worker LambdaではFastAPIは利用しない。

## 採用理由

- ルート・HTTPメソッド・リクエスト/レスポンスの型を宣言的に管理できる。
- Pydanticで入力のバリデーションを一元化できる。
- API数や仕様が増えた場合も拡張しやすく、OpenAPIによる仕様化に向いている。

## 不採用案と理由

- **Python標準のLambdaハンドラーで全ルート分岐**: 初期の依存管理は軽いが、APIが拡張した場合のルート・バリデーション・仕様管理を自前で実装する必要がある。
- **エンドポイントごとにFastAPIアプリを分割**: 小規模な3ルートに対して実装/デプロイ管理が増え、現時点でメリットが小さい。

## 影響・留意点

- `fastapi`、`mangum`、依存パッケージをZIPまたはコンテナに同梱する。Linux互換ビルド、依存バージョン固定が必要。
- FastAPIを採用してもBearerトークンの真偽や顧客別認可は自動では実装されない。
- 本番公開する `/docs` / `/openapi.json` の可否と、標準422エラーをAPI仕様にどう統一するかを決定する。

## 再検討条件

APIの規模縮小、起動時間や依存パッケージ制限が顕著になる場合、あるいは運用基盤が変わる場合。

## 経緯

2026-10-07に標準ハンドラー案を比較した後、2026-10-13の会話でFastAPI採用を明確に指定された。
