# セキュリティ・監査設計

## 公開API・認証

| 対象 | 設定・処理 |
| --- | --- |
| API Gateway | Regional REST API、HTTPS、APIキー要求なし |
| AWS WAF | REST APIステージにWeb ACLを関連付け。マネージドルール、`/auth`のレート制限を設計 |
| API Lambda | 保守キー＋顧客名の照合、JWTの発行・検証、ジョブの顧客所有者チェック |
| Secrets Manager | JWT署名秘密鍵を保管。取得できるのはAPI Lambdaのみ |
| S3 | Block Public Access、SSE-S3、短命な署名付きURLでJSON配信 |
| DynamoDB | 標準の保存時暗号化を使用。PITRを設定する |

- JWTは署名、`iss`、`aud`、`exp`、顧客IDを検証する。鍵のローテーション・失効方式は詳細設計で定義する。
- WAFのルールはCountで誤検知を確認してからBlockへ移行する。
- JWTや保守キーの認証だけに依存せず、`GET /jobs/{jobId}`では必ずジョブ所有者を検証する。

## 権限分離

| 主体 | 主な権限 | 許可しない操作 |
| --- | --- | --- |
| API Lambda | 顧客照合、ジョブ作成・照会、Worker起動、署名URL生成、JWT鍵取得 | Bedrock直接実行・請求実績の任意更新 |
| Worker Lambda | Bedrock呼び出し、ジョブ状態更新、S3保存、使用量イベントの新規登録（設計案） | JWT署名鍵取得・既存使用量の通常更新 |
| 運用・デプロイ担当 | 担当作業に限定。実行ロールとは別に管理 | 不要な`iam:PassRole`・データ変更 |

DynamoDBの`PutItem`単独では上書きを防げないため、使用量イベントには条件付き書き込み・冪等性を組み合わせる。

## ログ・検知

| 対象 | 用途・設定 |
| --- | --- |
| CloudWatch | API Gatewayアクセスログ、Lambda実行ログ、顧客・ジョブ単位のアプリ監査ログ、障害アラーム |
| CloudTrail | AWS操作の管理イベントをS3へ継続保存。重要なDynamoDB・S3操作のデータイベントを選択 |
| GuardDuty | AWS環境の脅威検出。検知結果はEventBridge→SNSなどで通知 |
| 監査用S3 | 生成JSONの保存先と分離し、公開アクセスを遮断。アクセス権と保存期間を制限 |
| AWS Budgets等 | AWS費用・Bedrock利用増加の検知 |

アプリ監査ログには`requestId`、`customerId`、`jobId`、操作・結果・時刻を記録する。**保守キー、JWT、入力全文、生成JSON、署名付きURL、署名鍵は記録しない。**

## 請求データの保護

- トークン使用量はBedrockの応答等からサーバー側で記録する。顧客から申告された値を請求根拠にしない。
- 使用量イベントの追記・重複計上防止、DynamoDB PITR、操作監査、請求確定明細の保全を組み合わせる。
- **専用KMSカスタマー管理キーは使用しない。** DynamoDB標準暗号化とS3 SSE-S3は利用する。
- S3 Object Lock、GuardDutyの追加保護、Bedrockモデル呼び出しログは必要性とデータ保護要件に応じて設定する。

## 設定値の未決定事項

WAF閾値／誤検知対応、JWT署名方式・有効期間・鍵更新、ログ保存期間、GuardDuty通知先、顧客別利用上限、アラーム閾値。

## 2026-10-19：複数企業向けの流量・公平性（追加候補）

SQS Fair Queuesを採用する場合は`MessageGroupId=customerId`とし、API側で認証済み顧客IDから設定する。Fair Queuesは特定企業による混雑影響を緩和するが、顧客別のリクエスト数・契約上限・実行並列数を強制する機能ではない。上限・課金・認可はアプリ側で管理する。
