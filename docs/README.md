## スマホで最初に確認する順番

最初の確認は次の3か所で十分です。図や大きな表は、必要になってから確認できます。

1. **[次の作業](current/次の作業.md)** — まず「1. 業務ルールと合格条件を決める」を読む。「利用者の承認が必要」の箇所が、最初に相談したい内容です。残りの2作業は見出しと成果物だけ確認してください。
2. **[今回のレビュー補足](current/構成設計.md#レビューで補足した設計案)** — 保守キー、停止と署名URL、WPF再起動、成果物、結果不明、品質、受付上限の7点を確認。気になる点だけメモすれば十分です。
3. **[現在の検討状況](current/検討状況.md)** — 決定済みの前提と、まだ提案・未決の内容が意図どおりか確認します。

**返してほしいこと：** 分かる範囲の業務ルールと、気になる点・違和感。未定のものは「未定」で構いません。全項目をその場で承認する必要はありません。

構造変更の候補は[次の作業の「2」](current/次の作業.md#2-状態遷移復旧構造変更案を具体化する)に集約しています。入口比較・構成図・69項目・過去資料は初回確認では後回しで大丈夫です。

## 今の結論

- **今回の設計前提：不透明トークン。** JWT採用は現在の前提ではない。期限・失効方式等は提案段階。
- **入口：最終決定前。** REST API＋WAF＋Event案とCloudFront＋WAF＋Web案を比較する。RESTは設定の簡潔さから暫定推奨。Webを不採用確定とは扱わない。
- **非同期ジョブ、Worker分離、DynamoDB、S3のJSON配信、WPFのポーリングは既存方針を継続。**
- **SQS Fair QueuesとOutboxは提案・検討中。** 比較図に描かれていても正式採用済みを意味しない。
- AWS構築・性能測定・料金実測の完了は確認していない。

## 更新するとき

1. 検討状況の「前提／継続方針／提案／未決」を更新する。
2. 決定事項はIDを維持し、構成図・設計本文にも反映する。

5. docs内のリンクと、GitHub mainへの反映を確認する。
