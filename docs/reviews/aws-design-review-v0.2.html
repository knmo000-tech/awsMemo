AWS Bedrock 非同期API
アーキテクチャ判断・レビュー準備資料

採用理由・不採用案・リスク・確認事項

対象：複数顧客企業向け WPFデスクトップアプリ → AWS → Bedrock → CSV生成 / トークン利用量による独自請求

01

既存保守キーを維持

REST API + WAFの導入でも顧客へのAPIキー再配布は不要。認証成功時にJWTを発行。

02

Lambdaは2関数

API受付とBedrock実行を分離し、処理時間・IAM権限・再試行を独立設計。

03

請求原本は最重要

トークン利用量の完全性、重複排除、監査、復旧を暗号鍵の追加管理より優先。

レビュー時の重要な前提：これは設計判断の説明用ドラフトであり、AWS構築完了・性能検証済みを意味しません。DBの物理設計、請求の例外整合性、障害対策の詳細は未確定です。

基本方針
保守キー認証→JWT発行→ジョブ受付→非同期Worker→Bedrock→CSVをS3に保存→状態照会・取得。

3. 認証：保守キー照合 → JWT発行 → 顧客認可

① POST /auth

顧客名（補助情報）＋既存保守キーをサーバーの登録データと照合。成功時だけ短命JWTを発行。

② POST /jobs

JWTの署名・期限・発行者・対象者を検証。customerIdはクライアントから受けずJWTから確定。

③ GET /jobs/{jobId}

JWT検証後にJobsのcustomerIdと一致することを確認。他社のジョブは存在を隠す応答も検討。

比較選択/不採用の理由弱点・改善点
既存保守キー＋自前JWT（採用）既存顧客の移行コストが少ない。API Gateway独自APIキーの配布も不要。後続APIでは保守キーを毎回送らない。保守キーがPCにあるためコピー・漏えいを想定。高エントロピー化、失効・ローテーション、試行制限が必要。
Cognito（代替）ユーザー認証・トークンライフサイクル等のマネージド化に利点。既存保守キー照合要件に合わせた移行・統合設計が必要。将来の利用者ID管理が要件化すれば再検討。
API Gateway APIキー（不採用）API Gatewayの利用量管理機能であり本人認証の代替ではない。既存保守キーと別の秘密情報を配ることになるため今回は不要。
上司への説明：「認証方式は新規ユーザー基盤の導入より既存資産との整合性を優先。ただし保守キーは“PCにある秘密”なので漏えいし得る。レート制限と失効機構は必須」です。
DESIGN REVIEW / PRIVATE DRAFT

4. JWTとSecrets Manager：鍵管理の根拠

採用理由

JWTの署名秘密鍵をソースコード・GitHub・クライアントから分離し、API Lambdaの実行ロールだけが必要な鍵を取得できるようにする。

Secrets Managerは取得・キャッシュを利用できる。Secrets Managerを使ってもJWTの検証・失効・鍵更新はアプリ設計が必要。[6]

代替案

固定の環境変数 / ソース埋込：単純だが漏えい・更新時の管理が難しいため見送る。

Cognito等：JWT発行管理を委任可能。ただし現段階では保守キー連携の実装負担を優先しない。

検証要素設計レビューで説明する内容
alg / kid利用可能な署名アルゴリズムを固定し、kidで署名鍵のバージョンを識別。未知のアルゴリズムを信用しない。
iss / aud / sub / exp想定発行者・対象API・顧客主体・有効期限を必ず検証。例として短い有効期限（15分程度）は設計案であり未確定。
鍵ローテーション旧トークン検証期間・失効手順・緊急ローテーションを設計。
秘密情報の閲覧権限API Lambdaにだけ必要なGetSecretValue、管理者側に編集・監査権限。Workerには不要。
残リスク：JWTを盗まれると期限まで不正アクセスされ得る。漏えい対策はTLS、ログの秘匿化、期限短縮、必要なら失効・再認証で補う。

5. API Gateway：REST API＋WAFを選んだ理由

候補メリットデメリット今回の判断
REST API + WAFAPI GatewayのREST APIステージにWAFを直接関連付け。機能が充実。HTTP APIより利用料が高くなる傾向。WAFルールの運用が必要。採用
HTTP API + CloudFront + WAFHTTP APIの低コスト性を活かせる可能性。CloudFrontを通らないAPI Gatewayへの直接アクセス経路を防ぐ追加設計が必要。不採用
HTTP API + WAF直接連携—API GatewayのHTTP APIにはWAF直接統合のサポートがない。選択不可

WAFで減らすリスク

保守キー総当たりの一部、既知パターンのWeb攻撃、大量リクエスト。マネージドルールとレートベースルールは初めにCountで誤検知を計測。

WAFでは減らせないリスク

正規JWTでの過剰Bedrock使用、顧客IDなりすましを伴う業務ロジック不備、トークン請求の整合性。顧客別クォータと認可はアプリ側で実装。

出典: AWS公式のREST/HTTP比較は、WAF統合がREST APIで利用できると明記。[1]

6. 実行基盤：FastAPI＋Lambda 2関数を選んだ理由

対象採用理由比較した代替案・見送り理由
FastAPI + Mangum3エンドポイントを宣言的に定義。Pydanticの型検証・OpenAPI仕様と整合。MangumがAPI GatewayイベントをASGIに変換。標準ハンドラーだけなら依存は少ないがルート・入力検証・仕様管理を自前で持つ。今回は将来拡張性を優先。
API Lambdaを1関数に集約ルーティングと認証・認可の共通処理を一元化。APIのデプロイ単位がシンプル。エンドポイントごとに分ければIAMが細かくなるが、3ルート時点で管理対象が増える。
Worker Lambdaを別関数Bedrock権限とタイムアウト・並列数をAPI側と分離。APIのHTTP応答待ちを避ける。同期一体型はAI実行に時間がかかるとタイムアウト・再試行・権限分離が難しい。
技術的注意：FastAPI/MangumはLambda標準ではないため依存をZIPまたはコンテナへ同梱。Linuxランタイム互換ビルドとバージョン固定が必要。
未確定：Workerを直接非同期Invokeするか、SQSを挟むか。課金の正確性を重視するため、これはレビューで優先確認したい設計判断。
DESIGN REVIEW / PRIVATE DRAFT

7. 非同期実行の最大リスク：欠落・再試行・二重請求

① 同じイベントを再実行

Lambdaの非同期Invokeはエラー時に既定で追加2回の再試行があり、同一イベントが重複到達する可能性もある。[2]

② Bedrock成功・記録失敗

モデルが利用料を発生させた後でLambdaが終了すると、アプリ側のusage記録が欠落し得る。再実行だけでは正確な復元を保証できない。

③ 起動受付後に滞留

非同期起動成功=実行完了ではない。イベント滞留や放棄、失敗送信先の運用が必要。[2]

構成案採用の妥当性追加すべき仕組み
直接非同期Invoke（現行の初期案）単純で導入が早い。低負荷で許容される失敗復旧条件なら可能。OnFailure Destination、ジョブ滞留検知、冪等性、再実行ルール、手動照合。
SQS + Worker（有力代替）メッセージの可視化・バッファ・再試行制御・DLQ運用がしやすく、今回の請求重視要件と相性がよい。SQSでも重複配送を想定。入力サイズ・再実行・冪等性は引き続き必須。
Step Functions（代替）複数段階の状態・分岐・再試行が明示できる。状態遷移・定義・監視の管理コスト。今の短いワークフローでは過剰になり得る。
設計レビューで提案：本番で「トークン利用量を1件も欠落させられない」に近い要件なら、直接非同期Invokeを無条件で確定しない。SQSなどのキュー化、課金レコードとジョブ状態の照合設計を比較して決める。

8. DynamoDB・S3・請求原本の設計理由

データ採用案と理由代替・留意点
Customers / JobsDynamoDB。顧客ID・jobIdで単純に取得、状態更新。マネージドで初期運用が軽い。結合・複雑集計が主ならRDS等も候補。最終判断にはアクセスパターン確認が必要。
UsageEvents（検討案）請求実績を状態が変わるJobsから論理的に分離。入力/出力トークン、モデル、価格バージョンを記録。物理的な別テーブルは未決定。RDBや単一テーブル設計との比較をDB詳細設計で実施。
生成CSVS3。非公開保管・署名付きURLで短時間だけ取得可能。LambdaやDBにファイルを長期保持しない。URLを知る人が有効期限内に利用できるため短命化・ログへの出力禁止が必要。[9]

使用量原本の書き込みルール案

記録対象：customerId / jobId / invocationId / modelId / inputTokens / outputTokens / 時刻 / pricingVersion / 訂正履歴。

基本原則：値はクライアント申告でなくBedrockのサーバー側usageを採用。[3]

追加書き込み：同一IDの上書きを防ぐ条件付きPutItem（例：attribute_not_exists）。[4]

重要：PutItem権限のみでは既存キーを書き換えられる。IAM＋アプリ条件式＋証跡を組み合わせる。

未解決の核心：Bedrockは実行されたが応答を受信できなかった場合、顧客に何を請求するか。推論ログ・料金突合・手動調査・訂正明細の運用が必要。
DESIGN REVIEW / PRIVATE DRAFT

9. IAM・KMS・暗号化の判断

対象必要な権限の例与えない権限・理由
API Lambda RoleCustomers/Jobs参照、Jobs新規作成、Worker起動、S3読取、署名鍵取得、ログ出力。Bedrock InvokeModelと請求UsageEvents任意更新を与えない。入口が侵害された場合の被害を限定。
Worker Lambda RoleBedrock InvokeModel、Jobs状態更新、CSVのS3保存、請求実績追記（案）、ログ出力。Customers秘密情報の取得、S3バケット全体削除、他テーブル変更などは不要。
運用・請求担当職務別の閲覧権限、限定的な訂正・復旧ワークフロー。作成から請求確定まで単独で無制限に原本を書き換える権限は避ける。

KMS顧客管理キーを今は採用しない理由

DynamoDBは既定でAWS所有キーによる保存時暗号化、S3はSSE-S3による保存時暗号化が適用される。[7][8]

KMSは暗号鍵の統制に有用だが、正規のPutItem権限によるトークン数変更は防がない。まず完全性対策を優先。

代替として優先する制御

IAM最小権限、条件付き追記、トークン実績の独立保管、操作ログ、請求確定版の証跡、PITRによる復元。

将来顧客契約で顧客管理鍵が必須になれば再評価。

10. 監査・検知・復旧：役割分担

サービス採用理由できないこと・残る対応
CloudWatchAPIの4xx/5xx、Lambda失敗、滞留ジョブ、顧客単位のアプリ監査イベントを観測。ログを出していない業務事象の証拠にはならない。ログマスキングと保持期間を設計。
CloudTrail誰のAWS権限で設定/データAPIが呼ばれたか追う。請求用DynamoDBのデータイベントは別途有効化。[5]顧客業務行為や更新前後の値の完全なスナップショットにはならない。
GuardDuty不正なAWS認証情報利用などの兆候を継続検知。[10]原則検知であり防御・対応・通知フローは別。追加保護プランはコスト評価が必要。
DynamoDB PITR誤更新/削除時に最大35日間の復元点を使って復旧。[11]不正な変更をリアルタイムで止めない。監査原本や請求確定履歴の長期保全とは別。
監査用S3CloudTrail/確定請求明細の保存先をCSV配布用バケットと分離。保存ポリシー、アクセス制限、改ざん防止、署名付きURLログ除外が必要。
判断：CloudWatch=運用・業務ログ、CloudTrail=AWS操作証跡、GuardDuty=脅威検知、PITR=復旧。重複投資ではなく目的が違う多層化。

13. 上司から想定される質問と短い回答

Q1. どうしてREST API？HTTP APIのほうが安いのでは？

A. WAFをAPI Gatewayへ直接接続でき、外部公開APIの防御構成を単純にするため。コスト差はトラフィックで再評価します。

Q2. APIキーを配布しなくて認証できる？

A. できます。API Gateway独自APIキーは使用せず、既存保守キーをFastAPIでDB照合し、JWTを発行します。

Q3. FastAPIはLambdaで動くの？

A. Mangum経由でASGIをLambdaイベントに橋渡しできます。外部依存の同梱とLinux互換のビルドが必要です。

Q4. なぜLambdaを2つに分ける？

A. API応答と長めのBedrock処理、IAM権限、タイムアウト・同時実行数を分離するためです。

Q5. なぜSQSがないの？

A. 初期案は最小構成です。ただし請求整合性の観点ではSQSを有力代替として残し、本番前に決めます。

Q6. 正確なトークン使用量はどこから？

A. WPFの自己申告でなく、Bedrockのサーバー側レスポンスのusageを記録します。失敗時の欠落は別途照合します。

Q7. DBが書き換えられたら請求は？

A. IAM権限分離、追記型イベント、条件付き登録、監査とPITRで抑止・検知・復旧します。構造は後続のDB詳細設計で確定します。

Q8. なぜKMSを入れない？

A. 既定の保存時暗号化はあり、顧客管理キーは正規権限による請求値の更新を防ぎません。まず改ざん・欠落対策を優先します。

Q9. GuardDutyとCloudTrailは重複しない？

A. CloudTrailは記録、GuardDutyは脅威の兆候検出。CloudWatchはアプリの業務ログ・障害監視で用途が異なります。

Q10. 一番大きい未解決事項は？

A. Bedrock成功後の利用量記録失敗、ジョブの再試行と二重請求、保守キー流出時の失効・顧客隔離です。
