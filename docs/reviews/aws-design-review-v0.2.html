AWS Bedrock連携システム — 設計レビュー

システム構成

業務構成図セキュリティ・監査図

WPF → WAF → API Gateway REST API → API Lambda（FastAPI + Mangum）→ Worker Lambda → Bedrock。生成JSONはWorkerがS3に保存し、WPFがジョブ状態をポーリングして署名付きURLから取得する。

構成・代替案の要点

論点採用方式代替案・確認事項
API入口REST API + WAFHTTP API + CloudFront + WAFは構成・迂回対策が増える
認証既存保守キー＋顧客名をDynamoDB照合 → JWTAPI Gatewayの追加APIキーは不要。キー管理・失効方法は要設計
API実装API Lambda 1関数にFastAPI + Mangumルート別Lambdaは関数・デプロイ管理が増える
AI実行独立Worker Lambdaを非同期Invoke同期実行は処理時間とAPIタイムアウトの影響を受ける
長時間処理Jobsに状態保存しポーリングSQS/Step Functionsは必要な信頼性・負荷に応じて追加検討
生成物JSONをS3へ保存し短命URLで取得API Lambda経由転送は採らない。JSON最大約1MBを想定
DBDynamoDBでCustomers / Jobs管理UsageEventsの物理別テーブル化は未決定
請求実績Bedrock由来の実使用量をサーバー側で記録クライアント申告値は請求根拠にしない
秘密情報Secrets ManagerでJWT署名鍵を管理鍵アルゴリズム、更新・失効は未決定
暗号化DynamoDB標準暗号化、S3 SSE-S3専用KMS顧客管理キーは採用しない
監視・監査CloudWatch、CloudTrail、GuardDuty保存期間・通知先・追加保護機能を設計する

重要な制御

  • API LambdaとWorker LambdaのIAM実行ロールを分離。Bedrock実行権限はWorkerだけ。
  • 顧客認可とジョブ所有者チェック。結果JSONは短命な署名付きURLで取得。
  • 利用量の追記・冪等性・監査・DynamoDB PITRで二重請求や記録漏れに備える。
  • ログへ保守キー、JWT、プロンプト全文、生成JSON、署名付きURLを出さない。

レビューで確定したい項目

  1. トークン消費後、JSON生成・保存・取得に失敗した場合の請求可否。
  2. Worker再実行・二重計上・使用量記録漏れとSQS等の要否。
  3. 保守キー・JWTの有効期限、漏えい・失効・鍵更新方法。
  4. 顧客別利用量上限、単価・計算方法、請求明細の保全。
  5. JSONスキーマ、保存期間、WAF閾値、障害通知先。
