## 前提・継続方針・未決を分ける

| 論点 | 現在の扱い | 次に確認・決定すること |
| --- | --- | --- |
| 認証トークン | **利用者指定の設計前提：不透明トークン** | 期限、保存、失効、顧客一括停止、キャッシュ |
| API入口 | **比較・最終選定前** | REST＋WAF＋EventとCloudFront＋WAF＋Webを同条件で検証 |
| 暫定推奨 | REST案を設定の簡潔さから暫定推奨 | Webの開発体験・性能・費用・運用が判断材料。Python移植費用を理由にしない |
| WAF | 両案の保護要件として維持 | RESTステージかCloudFrontに関連付け、迂回防止を検証 |
| 非同期処理 | API受付と生成Workerを分離する既存方針を継続 | 配送方式と回復手順、実行制限 |
| SQS Fair Queues | **導入推奨・検討中** | 採否、並列数、可視性、DLQ、公平性の評価 |
| Outbox・配送Lambda | **今回の詳細設計の提案** | 直接送信＋回復との比較、再配送・長期停止時の回復 |
| DynamoDB | 顧客・ジョブ・使用量管理の既存方針を継続 | Sessions、物理テーブル、キー・索引、整合性 |
| 生成物 | JSONを非公開S3に保存し認可後に署名URLで取得 | Schema、保持期間、期限切れ時の再発行 |
| 入力S3保存 | **提案** | 保存可否、機微情報、保持と孤立データ清掃 |
| 残量・請求 | サーバー由来の使用量記録は既存方針。予約・精算は提案 | 単位、単価、失敗・再推論・取得失敗の請求条件 |
| 暗号化 | 標準暗号化利用、追加CMKを採らない既存判断を継続 | 契約・データ要件変更時に再評価 |
| 秘密管理 | JWT署名鍵は今回の方式では不要 | 他のサーバー秘密情報がある場合の保管先・更新 |
| 監視・監査 | CloudWatch／CloudTrail／GuardDuty等の利用方針・計画 | 対象範囲、保持、閾値、通知先、運用担当 |
| 規模 | 約100社、月1万／10万／20万ジョブを検討上の仮定として利用 | 実際のピーク、ポーリング回数、目標待機・完了時間 |

この表の「方針」はAWSに実装済みという意味ではない。構築・デプロイ・負荷試験・費用実測は未確認。最新資料は設計たたき台で、API契約・IaC・本番パラメータの確定版ではない。

## 次の作業は3つ

1. **業務ルールと合格条件**：認証、請求、保存・停止、JSON品質と時間・予算。
2. **状態遷移・復旧・構造変更案**：停止地点別の回復、WPF再起動、試行別成果物、受付上限。
3. **最小構成での検証**：品質・障害復旧・負荷・運用を実測して採否を判断。

成果物・完了条件・承認対象・構造変更候補は[次の作業](次の作業.md)にまとめる。承認不要の資料・仕様案・試験準備は先行できる。69項目は番号順に進める作業列ではなく、漏れ防止の[詳細チェックリスト](決定事項一覧.md)として維持する。担当者・期限は未割当。
