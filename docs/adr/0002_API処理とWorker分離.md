# ADR-0002: API受付とBedrock実行を2つのLambdaに分離する

- **日付**: 2026-10-07
- **ステータス**: 採用（設計確定）、実装未確認

## 背景

WPFから保守キーで認証し、Bedrockに文字列を送信してCSV結果を取得する。モデル実行には時間がかかるためAPI呼び出しと処理実行を分離したい。

## 決定

- **API Lambda（FastAPI + Mangum）**: `POST /auth`、`POST /jobs`、`GET /jobs/{jobId}` を1関数で扱う。
- **Worker Lambda（Python）**: 非同期Invokeで起動し、Bedrock利用、CSV保存、ジョブ状態更新を担う。
- ジョブ状態は `QUEUED → RUNNING → SUCCEEDED/FAILED` で管理する。
- 各LambdaのIAM実行ロールを分離。API Lambdaには `bedrock:InvokeModel` を付与しない。

## 採用理由

- Bedrock処理時間とHTTPリクエスト処理を分離できる。
- IAMの最小権限が整理しやすい（API Lambdaが直接Bedrockを使わない）。
- Workerだけのタイムアウト・同時実行数・エラー監視を独立して設計できる。
- APIの3ルートを1つのアプリとして保守できる。

## 不採用案と理由

- **全処理を1つの同期Lambdaに統合**: 時間がかかるBedrock処理で応答タイムアウトや再試行設計が難しくなる。
- **APIルートごとに別Lambdaを作る（計3+Worker）**: 更に細かな権限分離は可能だが、初期段階では関数数・デプロイ・設定の管理が増える。
- **初期からSQSやStep Functionsを追加**: 再試行・障害隔離などに利点があるが、まず要求される処理量と耐障害性を確認したい。将来採用の余地を残す。

## 影響・リスク

非同期Invoke受付成功はジョブ完了を保証しない。失敗時の整合性、重複実行の冪等性、滞留検出、Bedrock消費トークンの二重課金回避を設計する。

## 出力形式に関する後続決定

2026-10-15：成果物はCSVからJSONへ変更。**非同期の2関数構成とS3保存は変更しない**（[ADR-0007](0007_JSON出力採用.md)）。このADRは当初の設計判断の経緯として維持する。

## 再検討条件

実行時間の増加、ジョブ数の急増、課金整合性に厳しい要件、非同期Invokeの取りこぼしや再試行管理の複雑化が生じた場合。

## 後続検討（2026-10-19）

複数企業からのジョブ集中、モデル別Bedrockクォータ、企業間の待ち時間の偏りを考慮し、[ADR-0009](0009_SQS公平キュー導入検討.md)でSQS Standard Fair Queues追加を推奨案として検討中。**2 Lambda分離の採用理由は変わらない。** このADRの「初期からSQSを採らない」は当時の履歴として残す。
