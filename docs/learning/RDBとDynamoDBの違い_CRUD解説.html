01 / DIFFERENCE最も大きい違いは、検索方法から配置を決めること

DynamoDBでは「どのキーで、どのまとまりを取得・更新するか」を先に決める。

観点RDBDynamoDB
データモデルテーブルの列・型・制約を定義し、行を保存テーブルに項目（Item）を保存。主キー以外の属性は項目ごとに異なってよい
主な設計の軸正規化・関係・整合性と、検索用の索引取得・更新のパターンと、それを満たすキー・索引・データ配置
関連データJOINと外部キーを利用できるテーブルJOIN・外部キー制約なし。アプリで組み立てるか、一緒に読める配置にする
検索SQLで条件・結合・集計を表現GetItem・Query・Scan等を使う。効率的な検索はキー・索引に依存
整合性制約・トランザクション等で保証条件付き更新・トランザクションと、アプリの検証で保証

RDBも索引・アクセス設計が必要。「RDBは何でも高速、DynamoDBは制約だけ」という比較ではない。DynamoDBにもSQL互換のPartiQLがあるが、JOINや検索の制約がなくなるわけではない。[1][2]

02 / KEYSPKは必須。SKはテーブルの定義による

主キーがPKのみ

customerIdだけで1項目を特定。

例：Customersの顧客情報。

／

主キーがPK＋SK

PKとSKの組で1項目を特定。

例：Creditsの顧客＋レコード種別。

PK＋SKのテーブルでは、全項目がPK・SKの両方を持つ。その他の属性は項目ごとに自由。ただしキーの属性名・型はテーブル定義に従い、業務上必要な属性・型はアプリで検証する。[2]

PKはパーティションキー、SKはソートキーという役割名。実際の属性名はcustomerId、jobId等でもよい。本資料のCreditsでは、属性名もPK・SKとする。

操作PK＋SKのテーブルで必要な指定
GetItem / UpdateItem / DeleteItem対象項目のPK・SKの両方
PutItem保存するItemにPK・SKの両方を含める
QueryPKの完全一致は必須。SK条件は任意
Scanキー指定不要。テーブル／索引全体を走査する

GSIをQueryする場合は、その索引に設定したPK・SKを使う。「PK・SK以外では一切検索できない」でも「全操作でPK・SKの両方が必須」でもない。[5]

04 / CRUD同じ操作をSQLとDynamoDBで比較する

各例は独立した操作で、結果は上の初期データを前提にする。SDK例はJavaScript v3のDynamoDBDocumentClientを使い、db・各Commandは初期化済みとする。実装言語の指定を意味しない。

C

Create：残量レコードを新規登録

顧客C003の残量100を登録する。同じ主キーがあれば失敗させる。

RDB SQL Server風

INSERT INTO Wallets
  (customerId, available, reserved)
VALUES ('C003', 100, 0);
-- customerId は主キー

DynamoDB SDK v3 · DocumentClient

await db.send(new PutCommand({
  TableName: "Credits",
  Item: {
    PK: "CUSTOMER#C003", SK: "WALLET",
    available: 100, reserved: 0
  },
  ConditionExpression: "attribute_not_exists(PK)"
}));
結果 C003のWALLETが1件増える。既存の同一PK＋SKは置換しない。

重要：PutItemはINSERT専用ではない。条件なしなら同じキーの項目全体を置換する。上の不存在条件は「このPK＋SKの項目がないこと」であり、「同じ顧客の項目が一切ないこと」ではない。[3]

R

Read：主キーで1件取得

顧客C001のWALLETだけを取得する。

RDB SQL Server風

SELECT customerId, available, reserved
FROM Wallets
WHERE customerId = 'C001';

DynamoDB SDK v3 · DocumentClient

const result = await db.send(new GetCommand({
  TableName: "Credits",
  Key: { PK: "CUSTOMER#C001", SK: "WALLET" },
  ConsistentRead: true
}));
// result.Item に取得結果
結果 { PK: "CUSTOMER#C001", SK: "WALLET", available: 100, reserved: 10 }

SKありのテーブルでは、GetItemにPK・SKの両方が必要。存在しなければItemなし。顧客内の予約・明細は返らない。[2]

U

Update：残量が十分な場合だけ減算

availableが20以上なら20減らす。事前SELECTと後続UPDATEを分離しない。

RDB SQL Server風

UPDATE Wallets
SET available = available - 20
WHERE customerId = 'C001'
  AND available >= 20;
-- @@ROWCOUNT = 0 なら更新なし

DynamoDB SDK v3 · DocumentClient

const result = await db.send(new UpdateCommand({
  TableName: "Credits",
  Key: { PK: "CUSTOMER#C001", SK: "WALLET" },
  UpdateExpression: "SET #a = #a - :n",
  ConditionExpression:
    "attribute_exists(PK) AND #a >= :n",
  ExpressionAttributeNames: { "#a": "available" },
  ExpressionAttributeValues: { ":n": 20 },
  ReturnValues: "ALL_NEW"
}));
結果 available：100 → 80。残量不足や項目なしなら条件エラーとなり、変更しない。

重要：UpdateItemは、項目がなければ新規作成にもなり得る。既存のみ更新したい場合は存在条件を付ける。条件判定と1項目の更新は原子的。実際のクレジット消費では増減明細等との一括更新も必要。[4]

D

Delete：精算済みの予約を1件削除

学習用の例として、J101の予約をstate＝SETTLEDの場合だけ削除する。

RDB SQL Server風

DELETE FROM Reservations
WHERE customerId = 'C001'
  AND jobId = 'J101'
  AND state = 'SETTLED';

DynamoDB SDK v3 · DocumentClient

await db.send(new DeleteCommand({
  TableName: "Credits",
  Key: {
    PK: "CUSTOMER#C001",
    SK: "RESERVATION#J101"
  },
  ConditionExpression: "#s = :settled",
  ExpressionAttributeNames: { "#s": "state" },
  ExpressionAttributeValues: { ":settled": "SETTLED" }
}));
結果 精算済み予約が1件消える。未精算・不存在なら条件エラー。WALLETやジョブは変わらない。

条件なしのDeleteItemは、項目が存在しなくても成功扱い。SQLの0行削除と条件エラーは扱いが異なる。外部キーに基づく削除制限・カスケード削除は自動ではない。実運用の予約・台帳削除は保持方針に従う。[2]

05 / QUERY一覧取得は「PKで選び、SKで絞る」

顧客C001の予約だけを取得する

RDB SQL Server風

SELECT * FROM Reservations
WHERE customerId = 'C001';

DynamoDB SDK v3 · DocumentClient

const result = await db.send(new QueryCommand({
  TableName: "Credits",
  KeyConditionExpression:
    "PK = :pk AND begins_with(SK, :prefix)",
  ExpressionAttributeValues: {
    ":pk": "CUSTOMER#C001",
    ":prefix": "RESERVATION#"
  },
  ConsistentRead: true
}));
結果 RESERVATION#J101 と RESERVATION#J102 の2件。WALLET・ENTRY・他社の項目は対象外。
取得したいもの検索方法
C001の全項目Query：PK＝CUSTOMER#C001。SK条件なし
C001の予約だけQuery：PK一致＋SKがRESERVATION#で始まる
さらにstate＝RESERVEDだけ上記QueryにFilterExpressionを追加。予約を読んだ後で除外
全顧客の特定状態ジョブ用途に合うGSI等の検索経路を設計。既存の顧客PKだけでは直接Queryできない

FilterExpressionは、SQLのWHEREと同じ感覚で性能を考えない。キー条件で読んだ後の絞込みなので、Filterを付けてもその読取容量は減らない。頻出検索なら索引・配置を検討する。[6]

Queryは最大1MBごとに返る。全件取得にはLastEvaluatedKeyでページングする。Filter後に0件でも続きがある場合がある。GSIは別のキー構造を持つ索引で、結果整合性による反映遅延がある。[5][6][7]

06 / DESIGN IMPACT今回のシステム設計で意識すること

論点設計上の扱い
取得パターントークン照合・顧客取得・顧客＋jobIdの状態照会など、キーが明確な操作を中心に設計する
テーブル間の関係ER図はIDによる論理参照。外部キー制約としてDBが保証する関係ではない
複数項目の整合性ジョブ作成・残量予約・明細等はTransactWriteItemsでまとめる。単独更新を並べるだけにしない
重複・並行実行不存在条件・残量条件・状態・試行ID・version等を更新条件へ含め、再送や競合を処理する
換算設定CreditRulesは不変の設定版と有効版を管理。適用版はジョブ受付時に固定する
検索・分析の追加必要な一覧・集計を先に洗い出す。キーで探せない要求はGSI・集計・別の分析経路を検討する

トランザクションも使える

RDBのBEGIN／COMMITに対応する一括更新がTransactWriteItems。同一アカウント・リージョン内の複数テーブルを対象に、全件成功または全件失敗にできる。対話的にトランザクションを開く形式ではなく、操作一式を送る。S3保存・SQS送信はこのトランザクションに含まれないため、別途回復経路を設計する。[8]

JOINの代わり

「顧客名付きジョブ一覧」なら、JobsをQueryしてCustomersをGetし、Lambdaで結合する。現在値を読むか、受付当時の値をJobsに保存するかは要件で選ぶ。別々の読取りは一つのスナップショットにはならない。

レビューでは、ER図に加えて「必要な取得・更新 → キー／索引 → 更新条件」を確認する。属性を自由に持てることと、業務ルールを自由にしてよいことは別である。
