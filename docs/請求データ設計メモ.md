# 請求データ設計メモ

Bedrockの**実際のトークン使用量**をサーバー側で記録し、独自単価で顧客に請求する。物理的なテーブル構造は詳細設計で決定する。

## データ領域

| 領域 | 記録するもの | 更新方式 |
| --- | --- | --- |
| `Customers` | 顧客ID・名称・保守キーの検証材料・有効フラグ | 管理者が変更 |
| `Jobs` | jobId、customerId、処理状態、結果S3キー、エラー | 処理に応じ更新 |
| `UsageEvents`（案） | 呼び出しID、顧客・ジョブID、モデル、入出力トークン数、単価バージョン | 原則追記 |
| 請求確定明細（案） | 対象期間、明細、計算結果、訂正履歴 | 確定後は原本保全 |

`UsageEvents`の**物理的な別テーブル化は未決定**。1テーブル設計とも比較する。

## 権限

| 主体 | 顧客・ジョブ | 使用量明細 |
| --- | --- | --- |
| API Lambda | 顧客参照、ジョブ作成・照会 | 書き込みなし |
| Worker Lambda | ジョブ状態更新 | 必要な新規イベント登録のみ |
| 請求集計処理（案） | 必要情報の参照 | 読み取りのみ |
| 管理者 | 管理業務に限定 | 訂正は通常更新と分離 |

- 使用量イベントは一意IDと`attribute_not_exists`等の条件付き書き込みで二重登録を防ぐ。
- `PutItem`を許可するだけでは既存レコードを上書き可能。IAM制限と条件付き書き込み・監査を併用する。
- Bedrock成功後のLambda停止や再試行に備え、利用量記録漏れと二重計上を調査・補正できるようにする。
- DynamoDB PITRを有効化し、重要な更新操作のCloudTrail証跡と確定明細を保全する。

## 未決定事項

- PK/SK・GSI、明細の物理的な分離、請求締めと訂正処理
- トークン内訳（入力・出力・キャッシュ等）、単価バージョン、計算・端数処理
- 再実行／部分成功／使用量記録失敗の補正、顧客別利用上限
- **Bedrockでトークンを消費したが、JSON生成・S3保存・結果取得に失敗した場合の請求可否**
- 請求明細・監査ログの保持期間と改ざん対策

## 2026-10-19：SQS追加時の二重計上防止

SQS Standard Fair Queuesは少なくとも1回配信を前提とする。SQSイベント起点のWorker再実行に対して、`jobId`/使用量イベントIDで一意性を保ち、DynamoDB条件付き書き込み・状態遷移制限を適用する。Bedrockが実際に複数回呼び出された際のAWS側コストと顧客請求可否は分けて扱う。SQS導入そのものは未確定。
