# ADR-0006: セキュリティ・監査サービスの役割分担

- **日付**: 2026-10-13
- **ステータス**: **導入計画・検討中**（個別サービスの実装・設定は未確認）
- **対象**: CloudTrail、GuardDuty、CloudWatch、Secrets Manager、AWS Budgets、アプリ監査ログ、S3 Object Lock

## 背景

複数顧客企業向けのインターネット公開サービスであり、保守キーと生成CSVを扱う。**顧客別Bedrockトークン実績を独自料金で請求する**ため、課金根拠データへの変更や不正利用を検出・説明できることが重要。

各サービスは互換ではない。**AWSリソース操作の監査、攻撃兆候の検知、API顧客操作の追跡、秘密情報の管理、料金異常の通知**を分けて設計する。

## 1. CloudTrail — 導入推奨／詳細検討中

- **目的**: IAM、Lambda、DynamoDB等のAWS API操作の証跡。
- **採用理由**: 権限変更や請求元データへのAWS API操作を後日追跡したい。
- **導入案**: 監査ログをS3に継続保存するTrail。必要なDynamoDBテーブル/S3バケットを対象にデータイベントを選択し、費用を試算する。
- **不採用案**: コンソールのイベント履歴だけに依存する案。長期監査やデータイベント記録に不足するため。
- **限界**: AWS APIの呼び出し主体を記録するもので、顧客がどの業務操作を行ったかやDBの更新前後の値を単独で保証しない。
- **再評価条件**: 監査保存期間、規制・契約要件、データイベントの発生量が確定したとき。

## 2. GuardDuty — 導入推奨／保護機能は詳細検討中

- **目的**: AWSアカウント・ワークロードの不審な挙動の検出。
- **採用理由**: IAMキー悪用やS3等への不審なアクセスを早期に把握したい。
- **導入案**: 基本のGuardDuty、必要に応じLambda Protection/S3 Protection。EventBridge→SNS等で検知結果を通知。
- **不採用案**: GuardDutyだけでWeb攻撃対策・監査保存・自動ブロックまで賄う案。用途が異なるので不適切。
- **限界**: 原則として検知中心。遮断や復旧は別途設計が必要。
- **再評価条件**: コスト、対象リージョン、検知通知の運用体制が確定したとき。

## 3. CloudWatch + アプリ監査ログ — 導入推奨／フォーマット詳細未確定

- **目的**: API Gatewayアクセス状況、Lambda障害、顧客ごとの認証・ジョブ・請求イベントの追跡。
- **採用理由**: CloudTrailのAWS側の証跡だけでは、どの顧客がいつジョブを登録・完了したかを監査できない。
- **導入案**: §requestId§ / §customerId§ / §jobId§ / §usageEventId§で関連づける構造化ログ。認証エラー、重複請求防止、不整合・滞留などにアラームを設ける。
- **不採用案**: CloudTrailログだけですべて代替する案。
- **限界**: ログに保守キー、トークン、プロンプト全文、CSV全文、署名付きURLを残さない。監査保全には保管期間・参照権限の設計が必要。
- **再評価条件**: 監査粒度、ログ量、保存年限が確定したとき。

## 4. Secrets Manager — 採用決定／JWT署名アルゴリズムは未確定

- **ステータス**: **採用（設計確定、未構築）**。FastAPIでJWTを自前発行する方式を採用するため。
- **目的**: JWTの署名秘密鍵などアプリの秘密情報を安全に管理。
- **採用理由**: ソースコード・GitHub・平文設定への鍵埋め込みを避け、権限分離・ローテーションを可能にする。
- **導入案**: API Lambdaの実行ロールだけに必要シークレットの `secretsmanager:GetSecretValue` を許可し、取得頻度・キャッシュ・更新運用を設計。Worker Lambdaには原則不要。
- **不採用案**: コードに固定秘密鍵を埋め込む案。
- **代替検討**: 非対称署名方式でKMSなどの署名APIを利用する案は、今回は専用KMS顧客管理キー不採用の方針やコストと整合する形で、**将来必要なら別途検討**。
- **実装前の課題**: HS256かRS256等の署名アルゴリズム、`iss`・`aud`・`exp`などのJWTクレーム検証、短い有効期限、`kid`による鍵識別、鍵ローテーション中の旧JWT検証期間、漏洩時の失効手順を設計する。
- **注意**: Secrets Managerに置くだけでJWTの署名・検証やローテーションのアプリ対応が自動実装されるわけではない。
- **再評価条件**: Cognito等のマネージド認証基盤へ移行し、独自署名秘密鍵が不要となった場合。

## 5. AWS Budgets / Cost Anomaly Detection — 導入推奨／上限設計未確定

- **目的**: AWS使用料金の予算超過や異常増加の早期把握。
- **採用理由**: Bedrock呼び出しの増加が請求に直結するため。
- **不採用案**: WAFだけでトークンの大量消費を制御する案。WAFは顧客別の課金クォータを把握できない。
- **補足**: 料金通知は自動的な利用遮断と同義ではない。顧客ごとの上限はアプリ側で制御。
- **再評価条件**: 顧客数・月間予算・SLAが確定したとき。

## 6. 請求証跡の保全 — 設計検討中

- **提案**: DynamoDB PITR、書き込み権限の制限、条件付き追記、CloudTrailのデータイベント、請求確定時の明細スナップショット。
- **S3 Object Lock**: 明細や監査ログの一定期間の改ざん・削除防止に有効だが、現時点では保持期間・運用負荷が未確定のため**採用未決定**。
- **請求イベントを単純な累積値で上書きする案**: 後日の検算・誤請求調査が難しく、原本を保持する方式より望ましくない。
- **Bedrockモデル呼び出しログ**: 入出力内容が記録される可能性があるため、無条件に有効化しない。機微な内容の保護や保存期間を検討してから決める。

## 経緯

2026-10-13: インターネット越しに複数顧客が使うことが判明し、Web入口の保護だけでなく顧客単位の操作監査・請求監査・誤請求対策が必要だと整理。CloudTrail、GuardDuty、CloudWatch、Secrets Manager等は採用**推奨**として文書化し、設定とコストは未決定として保持。

2026-10-13: 自前JWT発行の方針が明確になり、**Secrets Managerの採用を確定**。CloudTrail、GuardDuty等の個別の導入・運用仕様は引き続き検討。
