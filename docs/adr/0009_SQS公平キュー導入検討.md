# ADR-0009: SQS Standard Fair Queues導入の検討

> **現在の適用範囲（2026-10-25）：** SQS Fair Queuesは導入推奨・検討中を維持。比較図への記載は採用決定ではない。Outboxも提案段階。 [検討状況](../current/検討状況.md) / [後続ADR-0010](0010_不透明トークン前提と入口方式の再評価.md)。以下は当時の判断記録。

- **検討日**: 2026-10-19
- **当時のステータス**: **導入推奨・検討中**（正式採用・運用パラメータは未確定）

## 背景と目的

100社程度の顧客企業がWPFアプリでボタンを押すたびにBedrock生成ジョブを1件要求する。API Gateway + API LambdaはAWSクォータの範囲内で同時受付でき、もとの直接非同期Invoke構成でも複数Worker Lambdaの並列実行は可能である。しかし、Bedrockモデルごとのリクエスト数/トークン数クォータ、利用集中、失敗時の再試行、企業間の待機偏りを管理するには、受付とWorker実行間にキューがあると扱いやすい。

## 推奨する構成（まだ正式決定ではない）

```text
100社のWPF
  └→ AWS WAF + API Gateway REST API
       └→ API Lambda（JWT検証 / ジョブ受付 / 状態照会）
            ├→ DynamoDB Jobs（QUEUED記録）
            └→ SQS Standard Queue（MessageGroupId=customerId）
                 └→ Worker Lambda（SQSイベントソース / 並列数を制限）
                      └→ Bedrock → S3（生成JSON）/ DynamoDB（ジョブ・使用量）
```

- SQS **Standard QueueのFair Queues**を利用し、**`MessageGroupId=customerId`**で企業を識別する。これにより特定企業の大量投入が他企業のメッセージ待機時間に与える影響を緩和することを狙う。
- FIFOキューではないため、企業内の順序保証や重複排除の保証はない。企業ごとの専用Worker・保証された並列実行枠でもない。
- SQSイベントソースの**最大同時実行数**でWorkerの実行流量を制御する。検証初期はバッチサイズ1とし、Bedrock側のRPM/TPMクォータ、平均/p95実行時間、エラー・再試行を加味して調整する。
- Visibility Timeout、再試行、DLQ、最古メッセージ滞留時間アラームを詳細設計で決定。
- DynamoDBへのQUEUED登録とSQS送信は単一トランザクションではない。片方のみ成功した状態の回復（Outbox、整合性スキャン等）と`Idempotency-Key`を設計する。
- Standardキューは重複配送が起こり得る。ジョブの条件付き状態遷移・使用量イベントIDの一意制約などで二重計上を防ぐ。推論の二重実行によるAWS料金が完全に回避できない失敗モードも別途検討する。
- 顧客ごとの厳密な実行並列数・日次/月次上限・契約プラン制御はFair Queuesに任せず、API/DynamoDB側で追加設計する。

## 検討した代替案

| 方式 | 評価 |
| --- | --- |
| API LambdaからWorkerを直接非同期Invoke | 現行の採用方式。コンポーネント数は少ないが、Bedrockの流量制御・企業間公平性・滞留監視を別途実装する必要 |
| **SQS Standard Fair Queues** | **今回の推奨**。企業間の待機偏りを単一キューで緩和でき、再試行・滞留の運用も改善 |
| SQS FIFO | 順序保証が要件でない本システムでは優先しない。企業ごとの逐次実行は不要 |
| 企業ごとのSQSキュー | 強い顧客別SLAや専用枠が必要なら検討。100社分の管理負荷が増える |

## 採用前に確かめること

1. モデル/リージョン別のBedrock RPM・TPM・最大同時呼出し、平均とp95実行時間。
2. ジョブ受付から生成開始までの目標時間と企業間の偏り。100社が同時利用する状況を想定した試験。
3. Lambda Worker並列数、SQSイベントソース設定、DLQ、リトライ、タイムアウト、メトリクスの決定。
4. ジョブ状態・使用量記録・キュー投入の失敗時に二重請求しないテスト。
